# TourFlow — фронтенд турфирмы

**Демо:** https://shinilornekora.github.io/tourflow-front/ (бэкенд эмулируется в браузере, входы: `anna@example.com`, `max@example.com`, `root@example.com`, пароль `password1`)

SPA для бронирования отелей с тремя ролями: **клиент**, **менеджер отеля** и **администратор**.
Бэкенд — микросервисы [tourflow](https://github.com/shinilornekora/tourflow); фронт ходит только в его `gateway` по `/api`. Контракт API описан в [`docs/API.md`](https://github.com/shinilornekora/tourflow/blob/main/docs/API.md) бэкенда.

**Стек:** TypeScript · React 18 · Effector (+ effector-react) · React Router · Vite · Vitest · Testing Library · MSW. Стиль — неоморфизм (чистый CSS, без UI-библиотек), есть тёмная тема по системной настройке.

## Возможности по ролям

| Роль           | Что доступно                                                                                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Гость          | Каталог отелей с фильтрами, карточка отеля, проверка свободных номеров на даты, вход и регистрация                                                                                          |
| Клиент         | Бронирование номера (с ключом идемпотентности), личный кабинет: сводка, «Мои заказы» с вкладками «Предстоящие» и «История», отмена брони до дня заезда, уведомления, профиль и смена пароля |
| Менеджер отеля | Только свои отели: редактирование данных, типы номеров (добавить, изменить, в архив), брони гостей со сводкой и фильтрами, отмена с обязательной причиной, журнал действий                  |
| Администратор  | Всё, что менеджер, по всем отелям, плюс **добавление новых отелей**, включение и отключение отелей, назначение и снятие менеджеров, смена ролей пользователей                               |

## Запуск всей системы одной командой (Docker, macOS / Windows / Linux)

Фронтенд и бэкенд поднимаются вместе из репозитория бэкенда [tourflow](https://github.com/shinilornekora/tourflow): его `docker-compose.yml` сам соберёт этот фронтенд прямо из GitHub.

```bash
git clone https://github.com/shinilornekora/tourflow.git
cd tourflow
docker compose up --build
```

Откройте http://localhost:3000. Подробности и демо-входы — в README бэкенда.

Только фронтенд в Docker (бэкенд уже запущен на этой машине, gateway на :8080):

```bash
docker build -t tourflow-front .
docker run --rm -p 3000:80 -e API_UPSTREAM=http://host.docker.internal:8080 tourflow-front
```

`Dockerfile` двухэтапный: webpack собирает прод-бандл (без демо-кода MSW), nginx раздаёт его и проксирует `/api` в gateway (`nginx/default.conf.template`, адрес задаёт переменная `API_UPSTREAM`). Базовые образы мультиархитектурные: собирается и на Apple Silicon, и на Intel.

## Запуск для разработки

Основной сборщик — **webpack** (`webpack/`: common, dev, prod). Vite оставлен вторым конфигом (`vite.config.ts`), чтобы сравнить настройки.

```bash
npm install
npm start              # webpack-dev-server на :3000, HMR, /api → gateway (VITE_GATEWAY_URL, по умолчанию :8080)
npm run start:mock     # то же без бэкенда: фейковый gateway на MSW в браузере
npm run build          # продакшен-сборка webpack в dist/
npm run build:analyze  # то же + webpack-bundle-analyzer
npm run dev            # Vite dev-сервер (второй сборщик), dev:mock — без бэкенда
npm run build:vite     # продакшен-сборка Vite
npm run build:pages    # демо-сборка для GitHub Pages
```

**Проверки:** `npm run typecheck` (tsc), `npm run lint` (ESLint), `npm run format:check` (Prettier), `npm run check` — всё сразу. Перед коммитом husky запускает lint-staged (eslint --fix + prettier на изменённых файлах) и проверку типов.

**Оптимизация прод-сборки webpack:** `mode: production` (минификация terser и tree shaking), `contenthash` в именах файлов, `splitChunks` с отдельным vendor-чанком React, `runtimeChunk`, ленивые страницы через `React.lazy` с именованными чанками, извлечение и минификация CSS, `hidden-source-map`. Демо-код (MSW) вырезается из обычной сборки через `DefinePlugin`. SVG до 4 КБ встраиваются как data URL.

## Тесты

```bash
npm test                    # все тесты
npm run test:unit           # юнит: модели Effector, HTTP-клиент, утилиты, UI-кит
npm run test:integration    # интеграционные: всё приложение против фейкового gateway
npm run coverage
```

- **Юнит-тесты** (`*.test.ts(x)` рядом с кодом) проверяют модели Effector в изолированном `fork()`-scope через `allSettled`: восстановление сессии, валидацию дат, повтор брони с тем же `Idempotency-Key`, деление заказов на предстоящие и историю, а также HTTP-клиент (один общий `/auth/refresh` на параллельные 401, разбор ошибок).
- **Интеграционные тесты** (`src/test/integration/*.int.test.tsx`) рендерят приложение целиком (роутер + Effector + UI) и проходят сценарии каждой роли. Сеть подменяет MSW: `src/test/gateway.ts` — in-memory gateway с теми же контрактами, что у бэкенда.

## Структура (Feature-Sliced)

```
src/
  app/        маршруты (createBrowserRouter), гарды ролей, layout, стили-неоморфизм
  pages/      страницы; у сложных рядом model.ts на Effector
  entities/   session, notification, карточки отеля и брони
  shared/     api (клиент + эндпоинты + типы), lib, ui-кит
  test/       MSW-gateway, фикстуры, интеграционные тесты
```

## Модель чтения броней

Списки, карточки и сводки броней отдаёт `booking-query`, который узнаёт о брони из Kafka с задержкой. Поэтому ответ команды (бронь, отмена) — источник правды: он сохраняется в `entities/reservation/model.ts` и сливается со списком из модели чтения по `version`. Новая бронь видна в кабинете сразу, а отменённая не «воскресает» из устаревшего списка. Интеграционные тесты проверяют это с включённым `db.projectionLag`.

Списки бэкенд отдаёт максимум по 50 записей на страницу, `fetchAll` собирает их постранично.

## Безопасность сессии

Access-токен хранится только в памяти HTTP-клиента, refresh-токен — в HttpOnly-cookie бэкенда. При 401 клиент один раз вызывает `/auth/refresh` (общий промис на все параллельные запросы) и повторяет запрос; после перезагрузки страницы сессия восстанавливается тем же refresh.

## Демо на GitHub Pages

На каждый пуш в `main` workflow `.github/workflows/pages.yml` собирает демо (`VITE_MOCK=1`) и кладёт его в ветку `gh-pages`. В демо работает тот же фейковый gateway, что и в интеграционных тестах; данные лежат в `localStorage` браузера и сбрасываются кнопкой «Сбросить данные». Глубокие ссылки работают через `404.html` (копия `index.html`).
